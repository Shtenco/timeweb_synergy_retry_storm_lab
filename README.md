# HTTP Retry Storm Lab — как защита API превращается в источник отказов

[![Python](https://img.shields.io/badge/Python-3.10%2B-555?style=flat-square)](https://www.python.org/)

**Практическое локальное исследование**: шесть клиентских политик против одного и того же реального HTTP-сервиса, воспроизводимые сбои, реальные TCP-запросы по `127.0.0.1`, сырые наблюдения, проверка инвариантов и графики, созданные Python.

## Главное наблюдение

> В экспериментальной конфигурации добавление **общего** `CircuitBreaker` к `retry budget + bulkhead` уменьшило медианную успешность операций с **56,25% до 32,92%**. Зависимый сервер получил меньше вызовов, но часть здоровых запросов была отклонена *до HTTP*. Это не означает, что circuit breaker плох сам по себе: параметры и гранулярность защиты необходимо проверять на собственном трафике.

Ниже все числа — **наблюдения одного локального стенда**, а не обещания SLA для облачного кластера. Каждый режим проверялся **трижды**; каждый запуск содержал **240 логических операций**.

| Политика | Успех, медиана | HTTP-вызовов / операция | p95 всех операций | Смысл |
|---|---:|---:|---:|---|
| Без повторов | 47,92% | 1,00× | 40,25 мс | Контрольный вариант |
| Немедленный retry (до 3 попыток) | 69,58% | 1,83× | 120,72 мс | Успех вырос, нагрузка тоже |
| Retry с full jitter | 69,58% | 1,83× | 159,20 мс | Не всегда быстрее простого повтора |
| Только circuit breaker | 32,08% | 0,39× | 4,79 мс | Быстрый отказ не равен успеху |
| Retry budget + bulkhead | 56,25% | 1,30× | 46,73 мс | Меньше попыток, умеренный результат |
| Retry budget + bulkhead + breaker | 32,92% | 0,41× | 15,18 мс | Чрезмерно общий breaker мешает восстановлению |

Медианы рассчитаны по трём отдельным прогонам. Результат зависит от доли и природы неисправностей, темпа запросов, timeout и настроек ограничителей. Ошибки намеренно вносятся в `src/retrystorm/faults.py`.

### Файлы, с которых стоит начать

- `src/retrystorm/server.py` — действующий локальный HTTP-сервер с ограниченной ёмкостью и телеметрией;
- `src/retrystorm/faults.py` — фиксированный на все политики сценарий: постоянные и временные 503, медленные ответы;
- `src/retrystorm/policies.py` — клиентские политики, токен retry budget, semaphore bulkhead и state machine breaker;
- `src/retrystorm/load.py` — генератор предложенной нагрузки, группировка по фазам, проверка числа запросов;
- `src/retrystorm/report.py` — CSV/JSON и SHA-256, независимая проверка результатов;
- `scripts/make_figures.py` — только Python/matplotlib, девять PNG с белым фоном;
- `tests/` — unit + integration-тесты на **настоящем localhost HTTP**;
- `results/experiment_18/` — полный набор измерений, сохранённый без выдуманной статистики;
- `docs/` — методика, ограничения переноса результатов, сценарный план статьи.

## Быстрый запуск

Нужен Python ≥ 3.10. **Никакой облачный аккаунт, токен или платный сервис не требуется.** Основной стенд работает только со стандартной библиотекой Python.

```bash
# из корня репозитория
PYTHONPATH=src python -m unittest discover -s tests -v

# полный опыт: 6 политик × 3 повтора × 240 операций = 4 320 операций
PYTHONPATH=src python -m retrystorm \
  --requests 240 --repeats 3 --workers 24 --rps 180 \
  --backend-capacity 8 --seed 41 --output results/experiment_18

# проверить согласованность исходных CSV и отчёта + SHA-256
PYTHONPATH=src python scripts/verify_results.py results/experiment_18

# отрисовать технические диаграммы (не нужна нейрогенерация)
python -m pip install 'matplotlib>=3.7'
python scripts/make_figures.py results/experiment_18 figures
```

На Windows PowerShell вместо `PYTHONPATH=src python -m ...` можно выполнить `python scripts/run_experiments.py ...`, затем `python scripts/verify_results.py ...`; запуск тестов: `$env:PYTHONPATH='src'; python -m unittest discover -s tests -v`.

> **Защитный барьер:** сервер привязывается только к `127.0.0.1`, клиент запрещает внешние HTTP-адреса, порт выбирает операционная система. Нагрузку нельзя случайно направить на чужой API без изменения кода.

## Методика в шести шагах

1. Каждый из шести режимов получает новый сервер и один и тот же набор из 240 ID, отправляемых с заданным темпом (180 операций/с, 24 клиентских потока).
2. Для ID от 40 до 199 действует неизменный заранее fault-plan; вне этого окна ответы здоровые.
3. Внутри окна отказов: 32% постоянных HTTP 503, 32% временных 503 на первой попытке, 15% медленных ответов (55 мс) и 21% нормальных ответов (по фиксированному модульному распределению).
4. Клиентская попытка ограничена 40 мс; общий бюджет операции — 190 мс; сервер способен одновременно обслуживать до восьми запросов.
5. Сохраняются **все** логические операции и **все** серверные обращения, включая неуспех, время, попытку и фазу опыта.
6. После каждой серии инварианты проверяют уникальность исходных ID и соответствие числа HTTP-попыток двум независимым журналам. При экспорте формируются SHA-256.

Важно: при высоком предложенном RPS фактическая скорость старта может отличаться от заданной из-за планировщика ОС. На этой машине прогон измеряет локальные потоки и loopback, **не** распределённую сеть, Kubernetes, production-сервис и не типовое облачное SLA.

## Как читать результаты, не обманывая себя

`p95_ms` относится ко **всем** операциям, включая мгновенные отказы circuit breaker, поэтому низкий p95 не равнозначен хорошему UX. `amplification < 1` означает, что часть пользовательских операций была **отброшена до HTTP**. Ни один механизм в статье не оценивается по одной цифре.

Отдельный режим `budget_bulkhead` нужен как контролируемая абляция. `protected` отличается от него **включённым breaker**; поэтому сравнение показывает цену именно этой добавки в выбранной постановке. Температура CPU, сетевой планировщик, другие типы ошибок и параметры breaker могут существенно менять цифры.

## Ключевые инженерные детали

**Circuit breaker** не просто хранит `OPEN`. У него есть `CLOSED`, `OPEN`, `HALF_OPEN` и ровно один пробный запрос после cooldown. Каждому разрешённому запросу выдаётся `BreakerPermit(epoch, is_probe)`; завершение, пришедшее из устаревшей эпохи, не может закрыть новое полузакрытое состояние. Это защищает машину состояний от гонки конкурентных запросов.

**Bulkhead** реализован семафором на исходящие HTTP-попытки, а не на пользователя целиком. Отклонение локальным bulkhead **не считается** отказом зависимого сервера в статистике breaker.

**Retry budget** хранит предел общего числа дополнительных попыток с потокобезопасным списанием. Уменьшение лимита снижает нагрузку, но может оставлять часть временных ошибок невосстановленными.

**Full jitter** детерминирован по SHA-256 (`seed`, `request_id`, `attempt`) ради повторяемости сценария. Это не криптографический механизм безопасности.
